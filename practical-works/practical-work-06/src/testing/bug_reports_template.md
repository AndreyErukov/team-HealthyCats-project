# Шаблон баг-репорта «бережно»

Используется как шаблон GitHub Issue.  
**Заголовок:** `[BUG-XX] Экран: краткое описание`

## Шкала критичности

| Уровень | Когда ставим | Пример |
| :--- | :--- | :--- |
| **Critical** | Приложение падает, данные теряются или утекают, основной сценарий невозможен | Ошибка 500 на `/today`, XSS, доступ к чужим привычкам |
| **High** | Функциональное требование (ФТ) работает неверно, но есть обходной путь | Лимит привычек не работает, пауза игнорирует даты |
| **Medium** | Неудобство, неверный или непонятный текст, ломается часть сценария | Внутренние имена полей в сообщении об ошибке |
| **Low** | Косметика, мелкие неточности, хвосты демо-режима | Подпись «Тестовая матрица» на статистике |

## Шаблон

**ID:** BUG-XX  
**Заголовок:** [Экран] Что не так  
**Критичность:** Critical / High / Medium / Low  
**ФТ / кейс:** ФТ-Х.X, TC-XX  
**Окружение:** ОС, браузер и версия, ширина окна, тема и размер шрифта, ветка и коммит

## Правила

1. Один баг — один Issue. Не склеивать разные дефекты.
2. Шаги должен повторить человек, который не видел баг. Указывай конкретные данные.
3. Метки в GitHub: `bug`, критичность (`severity: high`), экран (`screen: today`).
4. Каждый Issue связываем с тест-кейсом и ФТ из `test_cases.md`.
5. После исправления тестировщик перепроверяет кейс и пишет в Issue результат, затем закрывает его.
